# 性能方法论：理论最优为什么不等于实测最优

> 适用范围：本仓库 lab0 / lab1 / lab5 / lab6 的基准数据与设计取舍。
> 目的：把"数据结构选择 → 复杂度分析 → 基准验证 → 按实测选型"的
> 完整经验固化下来，避免下次再被大 O 的假象误导。

## 1. 结论先行

- 大 O 只数"操作次数"，不数"每次操作多少钱"，也不保证被优化的操作
  就是热点。
- 理论能否兑现，取决于三件事：
  1. 被优化项在端到端时间中的占比（Amdahl 定律）；
  2. 渐进项在自己的真实工作区间是否已经主导；
  3. 常数项、内存层级、分配器成本是否被忽略。
- 正确姿势：保留基线实现 → 同负载实测 → 找交叉点 → 按真实分布选型。

## 2. 案例一：lab5 ARP 缓存 A/B

### 2.1 数据（Release，min of 5）

tick 空转（无过期，ns/tick）：

| n | A：map + 全表扫描 | B：有序 list + 索引 |
|---:|---:|---:|
| 1 | 1.2 | 1.2 |
| 8 | 3.3 | 1.2 |
| 64 | 39.4 | 1.2 |
| 512 | 375.6 | 1.2 |
| 4096 | 10040.6 | 1.2 |

其它负载：

| 负载 | n | A | B |
|---|---:|---:|---:|
| 批量过期，ns/条目 | 64 | 9.6 | 21.2 |
| 批量过期，ns/条目 | 4096 | 8.8 | 18.7 |
| 刷新，ns/次 | 64 | 4.1 | 6.2 |
| 刷新，ns/次 | 4096 | 3.8 | 6.2 |
| realistic，ns/tick | 8 | 25.3 | 25.3 |

### 2.2 三个反直觉点

1. **批量过期：摊销优势在最坏情况下消失。**
   B 的 tick 是 O(k)（k = 真正过期的条目数），A 是 O(n)；但突发过期时
   k = n，两者都退化为 Θ(n)，"少遍历"的优势没有了，只剩常数差。
   B 每删一条要做两次释放（`list::pop_front` 销毁节点 +
   `unordered_map::erase` 销毁节点），A 只做一次 `erase`。
   实测差约 10–12 ns/条目，正好是一次 glibc `free` 的量级。
   B 的优势区间是 **k ≪ n**（零星过期），不是"一次全过期"。
2. **刷新：O(1) 与 O(1) 不等价。**
   两边都是哈希 O(1)，但 B 的路径是 `find → iterator → 解引用 →
   splice → 写节点`，且 list 节点与 map 节点分两次分配、通常落在
   两条 cache line；A 是 `find → 直接写值`。理论把"维护第二份索引"
   当成免费，实际每条目多一次分配和一次间接寻址。
3. **realistic：被优化的不是热点（Amdahl）。**
   每 tick 8 次 `lookup` 约占 20 ns，tick 扫描在 n = 8 时只有 3.3 ns
   （约 13%）。B 把 3.3 省到 1.2，但它的 lookup 多一层迭代器解引用、
   刷新也更贵，正好抵消。即使把 tick 优化到 0，端到端最多快 13%。

### 2.3 理论兑现的地方

tick 空转随 n 增长：n = 4096 时 A 为 10.0 µs，B 为 1.2 ns，相差约
8400 倍；交叉点大致在 n ≈ 2–8。结论不是"理论没用"，而是
**理论只在它假设的区间成立**。

## 3. 案例二：lab0 deque vs 环形缓冲

| 操作（Release） | deque | vector 环形缓冲 | 差距 |
|---|---|---:|---:|
| write，64 B–64 KiB | 0.233–0.037 ns/B | 0.076–0.022 ns/B | 1.7–3.1× |
| peek，64 B | 0.400 ns/B | 0.194 ns/B | 2.07× |
| peek，≥1 KiB | 0.196–0.206 ns/B | 0.006–0.015 ns/B | 13.8–32.9× |
| pop，64 B | 0.062 ns/B | 0.054 ns/B | 1.15× |
| pop，64 KiB | 0.017 ns/B | < 0.0005 ns/B | 304.8× |
| read+write，64 B→4 KiB | 0.465→0.229 | 0.252→0.019 | 1.9→12.0× |

同一个"vector 更好"的结论，在不同 chunk 下强弱差 100 倍：

- **小 chunk 的 peek 只快 2.07×**：两种实现都被返回 `std::string` 的
  堆分配支配——接口强制的固定成本盖过了数据结构差异。
- **大 chunk 的 peek 快 13.8–32.9×**：deque 的逐字节迭代器循环成为
  瓶颈，固定成本被摊薄。
- **pop 的 304.8×**：O(k) vs O(1) 是真正的渐进项，理论完全兑现。

## 4. 案例三：lab1 map vs 环形缓冲（含位图变体）

- **典型段长（64 B–1 KiB）**：环形缓冲快 1.4–9.2×；`streaming` 稳态
  2.4×（0.022 vs 0.053 ns/B）。
- **原因**：map 每段约 3 次堆分配（64 B 段 4096 个 → 12288 次/run），
  环形缓冲在构造后 0 次；perf 显示 map 指令数是 ring 的 3.3–3.5×，
  cycles 约 2.1×。差距主要来自分配与每段工作量，而不是缓存命中率。
- **reverse（map 的最坏情况）**：每来一个新段都要与已有大段拼接，
  呈 O(n²)，环形缓冲与到达顺序无关——渐进项主导时理论准确。
- **超大块（16–64 KiB）且段数很少时**：情形反转，map 反而快
  （用时为 ring 的 0.6–0.9×）。此时分配开销被摊薄，而 ring 需要
  额外扫描位图并多一遍内存访问。工作区间变了，胜负也变了。
- **bitset vs byte 位图**：bitset 内存省 8 倍（C/8 vs C），但 Release
  吞吐差异在 ±15% 内，Debug 小段长下反而慢 10–25%——标量字扫描
  对不上 glibc `memchr` 的 SIMD。空间最优 ≠ 时间最优。
- **缓存指标的陷阱**：map 的 L1d miss **率**更低（4.06% vs
  10.7–11.6%），但绝对 miss/字节高约 40%。只报 miss 率会得出相反
  结论，必须报"每字节 / 每操作"的绝对量。

## 5. 案例四：lab6 路由表（线性 / Patricia 树 / 分桶哈希）

### 5.1 设置

- 三种实现共用 `RouteEntry` 与同一套掩码语义；计时前先逐查询对拍，
  确认结果完全一致，再比较耗时。每项取 5 次最小值（n > 50000 时为
  2 次，控制总时长），Release 构建。
- 随机路由表：10% 为 /8–/16、55% 为 /17–/24、35% 为 /25–/32，
  外加一条 0.0.0.0/0；查询一半命中已知前缀、一半为随机地址。
- 数据来自 `./apps/router_benchmark <n> ...`，下表为单次查找耗时（ns），\n  n 为表项总数（含默认路由）。

### 5.2 数据

| n | vector 线性 | Patricia 树 | 分桶哈希 |
|---:|---:|---:|---:|
| 5 | 14.8 | 13.9 | 33.8 |
| 9（本 lab 真实规模） | 18.2 | 19.3 | 43.0 |
| 17 | 24.6 | 23.0 | 61.0 |
| 33 | 42.1 | **24.9** | 89.3 |
| 129 | 121.7 | **34.1** | 183.8 |
| 513 | 457.9 | **55.4** | 246.6 |
| 4097 | 4605.4 | **106.3** | 322.0 |
| 16385 | 18330.2 | **145.6** | 295.4 |
| 65537 | 116382.8 | **205.5** | 346.2 |

构建与内存（n = 65537）：线性 8.6 ms；Patricia 21.1 ms、118742 个
节点（约 1.8× n）；分桶哈希 8.3 ms，但每条目一次 `unordered_map`
节点分配。

### 5.3 四个反直觉点

1. **本 lab 的真实规模下，树没有赢。** 官方模拟网络合计只有 9 条路由
   （单台路由器最多 4 条）：线性 18.2 ns，树 19.3 ns，哈希 43.0 ns。
   n ≤ 17 时线性与树的差异都在 10% 以内（噪声量级），n ≥ 33 后树才
   稳定领先；交叉点大致在 **n ≈ 20–30**，正好落在实验规模右侧——
   手册允许 O(N) 扫描不是偷懒。
2. **分桶哈希的"O(1)"比树慢 1.7×，小表时慢 2 倍以上。** 它每次要
   扫 33 个长度的位图，命中后再做一次 `unordered_map::find`，而单次
   哈希查找本身就有 10–20 ns 量级；复杂度把"33 次判断 + 若干次
   哈希"记作 O(1)，常数却比树的几次指针跳转更贵。
3. **树的绝对耗时仍随 n 上涨（13.9 → 205.5 ns，约 15×）。** 节点数
   1.8× n、节点分散在堆上，每层一次 cache miss；它不是"O(1)"，
   而是 O(深度) 加内存层级。但相对线性扫描仍是 566×
   （n = 65537：116 µs vs 206 ns）。
4. **构建与内存的取舍方向相反。** 树构建是线性扫描的 2.5×、内存
   1.8×；哈希构建最快但内存最贵。路由表频繁更新时，"查询更快"
   未必是端到端最优；只有读多写少的表才该按查询成本选型。

### 5.4 选型结论

- 默认用 Patricia 树，保留线性实现作基线与小表可选方案；分桶哈希
  仅作对照，用于说明"哈希 ≠ 快"。
- 用 `RoutingTable` 接口隔离算法，`Router` 只改一行即可切换；一次
  虚函数调用的开销远小于被优化的查找成本。

## 6. 原因清单（七类）

1. **单位操作成本不同**：一次哈希删除 + `free`（约 10–20 ns）≠
   一次指针比较（约 0.5 ns）；复杂度把两者都记作 1。lab6 中一次
   `unordered_map::find` 的开销就抵得上几十次指针跳转。
2. **小 n 时低阶项主导**：O(n) 在 n = 8 时只有 3.3 ns，"更好的复杂度"
   绝对值可能更差；先找交叉点。lab6 的交叉点在 n ≈ 20–30，官方
   9 条路由的规模远在交叉点左侧。
3. **摊销 ≠ 最坏**：摊销分析不覆盖突发；B 的 O(k) 只在 k ≪ n 时占优。
4. **内存层级与分配器**：每条目分配几次、释放几次、几条 cache line，
   往往比 Big-O 更影响 10–100 ns 量级的结果。lab6 的树节点为表项的
   1.8×，查找从 14 ns 涨到 206 ns，涨的主要是 cache miss。
5. **Amdahl / 热点错位**：占比 13% 的项优化到 0 也只值 13%。
6. **接口/环境固定成本**：`std::string` 分配、哈希查找、系统调用等
   与数据结构无关的成本可能占大头。
7. **实现常数与测量方法**：SIMD vs 标量、分支与数据分布、
   `-O3`（g++）vs `-Og`（clang）、min-of-N、噪声。

## 7. 设计时的问法（checklist）

- 我优化的操作占端到端时间多少？如果不是热点，先停手。
- 真实的 n / k / 段长分布是什么？交叉点在哪一侧？
- 每次操作分配几次、释放几次？节点分散在几条 cache line？
- 有没有接口强制的固定成本，会不会盖过我的优化？
- 最坏情况（批量过期、反序到达、全量重传）怎么办？
- 多出来的不变量与维护成本（如 B 的"链表顺序 == 到期顺序"）值得吗？
- 数字是否来自 Release、同二进制基线、min-of-N？Debug 只作冒烟。

## 8. 基准方法（本仓库可复用）

- **同二进制保留旧实现作基线**：lab0 `DequeByteStream`、lab1
  `MapStreamReassembler`、lab5 `ArpCacheScan/ArpCacheLru`。
- **相同负载、整型模拟时钟**；计时区只包含被测操作；正确性在计时区
  外校验（内容一致、计数器一致、A/B 结果逐条相等）。
- **每项取 N 次最小值**；Debug 跑小规模并注册进 ctest 作冒烟，
  Release 跑大规模取正式数据。
- **报 ns/op + 分配次数/字节**，能上 perf 时补 cycles、instructions、
  L1 绝对 miss/字节。
- **扫描参数找交叉点**（n、chunk、段长），不要只测一个点。
- 注册方式：`add_test_exec(<name>)` + `add_test(NAME t_<name> ...)`；
  命令行暴露 `[n] [reps] [ticks]` 方便外部复测。
- lab6 `apps/router_benchmark`：命令行 `[n ...]` 指定路由表规模，
  计时前先对三种实现逐查询对拍；未注册进 ctest，避免拖慢
  `make check`，只需手动跑一次留档。

## 9. 何时该相信理论（反向案例）

- lab0 pop：O(k) vs O(1)，64 KiB 时 304.8×——渐进项主导。
- lab1 reverse：map 的 O(n²) 拼接如期出现。
- lab5 tick 空转 n = 4096：10.0 µs vs 1.2 ns，约 8400×。
- lab6 路由表 n = 65537：线性 116 µs vs Patricia 206 ns，约 566×；
  但 n = 9 时线性 18.2 ns 略快于树的 19.3 ns（差异在噪声内）——
  区间决定胜负。

理论不是错的，而是**有适用区间**；实测的作用是确认自己是否在区间内，
并量出交叉点与常数。

## 10. 工程成本也是成本

- B 多一条必须始终成立的不变量（刷新必须 `splice` 到尾部）；漏写会
  删掉仍有效的映射，正确性风险与调试成本高于性能收益。
- A 简单、bug 面小，且在本实验规模下实测不差——简单优先有性能之外
  的充分理由。
- lab6 的 Patricia 树约 200 行，远超手册"25–30 行"的预期；压缩边
  校验、祖先插入等路径 `make check_lab6` 覆盖不到，必须自建随机
  对拍兜底。
- `RoutingTable` 抽象多了一次虚函数调用与 `unique_ptr` 间接，但换来
  一行切换实现；相对被优化的查找成本可忽略。
- 写 writeup 时固定记录：结构选择与被否方案、复杂度与内存取舍、
  基准方法、原始数据表、结论。
